# Documentation Skill

## Name
Comprehensive Documentation Standards for NutriChef AI

## Description
This skill provides comprehensive guidance for creating production-ready documentation for the NutriChef AI platform. It covers code documentation (docstrings, comments), API documentation (OpenAPI/Swagger), README files, architectural decision records (ADRs), and user-facing documentation.

## Purpose
To ensure all code, APIs, and features are thoroughly documented following NutriChef AI documentation standards, making the codebase maintainable, onboarding efficient, and APIs discoverable.

## When to Use
- Documenting new functions, classes, or modules
- Creating API endpoint documentation
- Writing README files for repositories or modules
- Documenting architectural decisions (ADRs)
- Creating user guides or developer guides
- Updating documentation after refactoring
- Documenting complex algorithms or business logic
- Creating onboarding documentation for new developers

## Inputs
- **Code to Document**: Functions, classes, modules, APIs
- **Audience**: Developers, users, stakeholders
- **Documentation Type**: Docstrings, README, ADR, API docs, user guide
- **Complexity Level**: Simple, moderate, complex
- **Examples Needed**: Code examples, usage examples, API examples

## Outputs
- **Docstrings**: Google-style docstrings for functions and classes
- **Code Comments**: Inline comments for complex logic
- **README Files**: Markdown documentation for repositories/modules
- **API Documentation**: OpenAPI/Swagger docs auto-generated by FastAPI
- **ADRs**: Architectural decision records in docs/adr/
- **User Guides**: Markdown documentation for end users
- **Developer Guides**: Setup, contribution, and development guides

## Best Practices

### 1. Docstring Standards (Google Style)
- Use Google-style docstrings for all public functions and classes
- Include: Brief description, Args, Returns, Raises, Examples
- Keep descriptions concise but complete
- Use proper type hints in function signatures (not in docstrings)

### 2. Code Comments
- Comment "why", not "what" (code should be self-explanatory)
- Explain complex algorithms and business rules
- Keep comments up-to-date with code changes
- Avoid obvious comments
- Use TODO, FIXME, NOTE for special annotations

### 3. API Documentation
- FastAPI auto-generates OpenAPI docs at `/docs` and `/redoc`
- Add descriptions to endpoints using docstrings
- Use Pydantic schema descriptions for field documentation
- Provide example requests and responses
- Document authentication requirements

### 4. README Structure
- **Title and Description**: What the project/module does
- **Features**: Key features and capabilities
- **Installation**: Setup instructions
- **Usage**: Basic usage examples
- **API Reference**: Link to API docs
- **Configuration**: Environment variables and settings
- **Contributing**: Contribution guidelines
- **License**: License information

### 5. Architectural Decision Records (ADRs)
- Document significant architectural decisions
- Use template: Context, Decision, Consequences
- Store in `docs/adr/` directory
- Number ADRs sequentially (001-adr-title.md)

### 6. Keep Documentation Updated
- Update docs when code changes
- Review docs during code reviews
- Use CI/CD to validate documentation
- Archive outdated documentation

## Common Mistakes

### ❌ Mistake 1: Missing or Incomplete Docstrings
```python
# BAD: No docstring
async def create_recipe(recipe_data: RecipeCreate) -> Recipe:
    recipe = Recipe(**recipe_data.model_dump())
    await recipe.insert()
    return recipe
```
**Fix**: Add comprehensive docstring
```python
# GOOD: Complete docstring
async def create_recipe(recipe_data: RecipeCreate) -> Recipe:
    """Create a new recipe in the database.
    
    Validates the recipe data and inserts it into the MongoDB recipes collection.
    Checks for duplicate titles before creation.
    
    Args:
        recipe_data: Recipe creation data including title, ingredients, instructions,
                     prep_time, cook_time, and servings.
    
    Returns:
        The created Recipe object with generated ID and timestamps.
    
    Raises:
        HTTPException: 409 if a recipe with the same title already exists.
        HTTPException: 500 if database insertion fails.
    
    Example:
        >>> recipe_data = RecipeCreate(
        ...     title="Chicken Alfredo",
        ...     ingredients=["chicken", "pasta", "cream"],
        ...     instructions="Cook pasta, add chicken and cream",
        ...     prep_time=15,
        ...     cook_time=30,
        ...     servings=4
        ... )
        >>> recipe = await create_recipe(recipe_data)
        >>> print(recipe.id)
        '507f1f77bcf86cd799439011'
    """
    # Check for duplicate
    existing = await Recipe.get_by_title(recipe_data.title)
    if existing:
        raise HTTPException(
            status_code=status.HTTP_409_CONFLICT,
            detail=f"Recipe with title '{recipe_data.title}' already exists"
        )
    
    recipe = Recipe(**recipe_data.model_dump())
    await recipe.insert()
    return recipe
```

### ❌ Mistake 2: Obvious Comments
```python

# GOOD: Explains why, not what
```

### Example 2: Class Docstring

```python
# backend/app/models/recipe.py
from beanie import Document, Indexed
from typing import List
from datetime import datetime

class Recipe(Document):
    """Recipe document model for MongoDB.
    
    Represents a recipe with ingredients, instructions, and metadata.
    Supports full-text search, ingredient filtering, and soft deletes.
    
    Attributes:
        title: Recipe title (indexed for search).
        description: Optional recipe description.
        ingredients: List of ingredient names.
        instructions: Step-by-step cooking instructions.
        prep_time: Preparation time in minutes.
        cook_time: Cooking time in minutes.
        servings: Number of servings the recipe yields.
        author_id: Reference to the User who created the recipe.
        created_at: Timestamp when recipe was created (UTC).
        updated_at: Timestamp when recipe was last updated (UTC).
        is_deleted: Soft delete flag (default: False).
    
    Collection:
        recipes
    
    Indexes:
        - title (ascending)
        - author_id (ascending)
        - created_at (descending)
        - (author_id, created_at) compound index
    
    Example:
        >>> recipe = Recipe(
        ...     title="Chicken Alfredo",
        ...     ingredients=["chicken", "pasta", "cream"],
        ...     instructions="Cook pasta, add chicken and cream",
        ...     prep_time=15,
        ...     cook_time=30,
        ...     servings=4
        ... )
        >>> await recipe.insert()
        >>> print(recipe.id)
        '507f1f77bcf86cd799439011'
    """
    
    title: Indexed(str)
    description: Optional[str] = None
    ingredients: List[str]
    instructions: str
    prep_time: int
    cook_time: int
    servings: int
    author_id: str
    created_at: datetime = Field(default_factory=datetime.utcnow)
    updated_at: datetime = Field(default_factory=datetime.utcnow)
    is_deleted: bool = False
    
    class Settings:
        name = "recipes"
        indexes = [
            "title",
            "author_id",
            [("created_at", -1)],
            [("author_id", 1), ("created_at", -1)]
        ]
```

### Example 4: Architectural Decision Record (ADR)

```markdown
# ADR 001: Use Beanie ODM for MongoDB Operations

## Status
Accepted

## Context
We need to choose an ODM (Object-Document Mapper) for MongoDB operations in the NutriChef AI backend. The application requires async database operations, type safety, and clean integration with FastAPI and Pydantic.

## Decision
We will use Beanie ODM for all MongoDB operations.

## Rationale

### Advantages
- **Async-First**: Built on Motor (async MongoDB driver)
- **Pydantic Integration**: Uses Pydantic v2 for validation
- **Type Safety**: Full type hints support
- **FastAPI Integration**: Seamless integration with FastAPI
- **Query Builder**: Pythonic query syntax
- **Active Development**: Well-maintained with regular updates

### Alternatives Considered

1. **Motor (raw driver)**
   - Pros: Lightweight, full control
   - Cons: No ODM features, manual validation, verbose queries

2. **MongoEngine**
   - Pros: Mature, feature-rich
   - Cons: Synchronous, no Pydantic integration, not async-first

3. **ODMantic**
   - Pros: Pydantic-based, async
   - Cons: Less mature, smaller community

## Consequences

### Positive
- Clean, type-safe database operations
- Reduced boilerplate code
- Better developer experience
- Automatic validation with Pydantic
- Easy to test with async fixtures

### Negative
- Learning curve for developers unfamiliar with Beanie
- Abstraction layer adds minimal overhead
- Tied to MongoDB (not database-agnostic)

### Neutral
- Requires MongoDB 4.0+ for full features
- Need to maintain Beanie version compatibility

## Implementation Notes

- All models inherit from `beanie.Document`
- Use `init_beanie()` in application startup
- Define indexes in model `Settings` class
- Use Beanie's query builder for type-safe queries
```
